# 要件定義書（草案）— Unified-File-Search-Tool

## 1. 目的
指定ディレクトリ配下の各種ドキュメント（PowerPoint / Excel / Word / PDF / Markdown / テキスト等）を対象に、入力した検索文字列で「ファイル内容」を横断検索し、結果を一覧表示・プレビューで確認できるデスクトップアプリを提供する。

## 2. 背景 / 課題
- フォルダ配下に散在する複数形式ファイルから、目的の記述を素早く発見したい
- 検索結果が出ても、該当箇所を開いて確認する手間を減らしたい（プレビューで直接確認したい）
- UX（一覧性、導線、操作回数の少なさ）を最優先したい
- 検索中に処理状況が見えないと不安になるため、進捗を明確に表示したい

## 3. スコープ
### 3.1 対象（やること）
- 指定ディレクトリ配下のファイルを列挙し、検索前に一覧表示する
- 検索文字列によりファイル内容を検索し、マッチしたファイルのみ一覧表示する
- マッチ箇所単位で選択でき、右側プレビューで該当箇所を強調表示（マークアップ）する
- プレビュー表示は「現物に近い見え方」を目標とし、画像や表も含めてHTMLで再構成して表示する
- すべてのプレビュー表示に対し拡大・縮小（±）および等倍（リセット）を提供する
- 選択されたファイルのみ、全体をプレビュー表示できる（フルロード）

### 3.2 非対象（当面やらない）
- ネットワーク共有やクラウド（SharePoint等）への専用対応
- 検索結果の自動エクスポート（CSV/Excel等）
- OCR（スキャンPDFの画像から文字抽出）

※非対象は要件固まり次第、見直し可能。

## 4. 利用環境 / 技術制約
- OS: Windows（前提）
- GUI: PySide6
- 依存管理: `uv`（`pip`は使わない）

## 5. 対象ファイル形式（初期）
- PowerPoint: `.pptx`
- Excel: `.xlsx`
- Word: `.docx`
- PDF: `.pdf`
- Text/Markdown: `.txt`, `.md`
- Log: `.log`（制御文字を含む場合も扱える）
  - 改行コード（`\n` / `\r\n` / `\r`）の違いにも対応し、表示上は正しく改行されること

### 5.1 テキスト系の共通取り扱い
- `.txt` / `.md` / `.log` は、改行コード（`\n` / `\r\n` / `\r`）の違いを吸収し、内部表現は `\n` に正規化した上で表示する

※旧形式（`.doc`, `.xls`, `.ppt`）や他形式は別途要件化。

## 6. 検索条件
### 6.1 表層（ON/OFFで即操作できる）
- 拡張子フィルタ（対象形式の選択）
- 大小文字区別（Case sensitive）
- 正規表現（Regex）
- 全文一致（完全一致）
- 一部一致（部分一致）

### 6.1.1 拡張子フィルタ（ポップアップ選択）
- 拡張子フィルタは「ボタン」からポップアップを開き、対象ディレクトリに存在する拡張子一覧を表示する
- 一覧の各拡張子の先頭にチェックボックスを表示し、チェック状態で対象を絞り込める
- ディレクトリ変更時は、拡張子一覧を再生成する

### 6.2 詳細設定（Advanced）
- 除外語（検索語とは別に、含まれる場合に除外する語）
- サブフォルダ検索の有無
- ファイルサイズ上限
- 更新日範囲

## 7. 一覧表示要件（左ペイン）
- 検索前: 指定フォルダ配下のファイル一覧を一覧表で表示
- 検索後: マッチしたファイルのみ表示

### 7.1 一覧のカラム
- 通し番号
- ファイル名
- 拡張子（ボタン）
- Path
  - 右クリックメニュー: 「ファイルを開く」「Pathをコピー」
- 検出数
  - 1ファイルにつき検出は最大50件まで読み取り
  - 50件を超えた場合は `50>` と表示
- インフォメーションチップ（ホバー）
  - 作者
  - 作成日

## 8. プレビュー要件（右ペイン）
- 上部に「マッチ箇所単位」のプルダウンを配置
  - 選択したマッチ箇所をプレビューで表示する
- ページ/シート切替UI
  - 通常はグレーアウト
  - 複数ページ（PDF等）または複数シート（Excel等）にマッチがある場合に有効化
- マッチ箇所は強調表示（誇張できる表現）
- 拡大/縮小（±）と等倍に戻すボタンを提供
- フルロードボタンを提供
  - 選択されたファイルのみ、全体をプレビュー表示する
  - 全体表示中も、マッチ箇所の強調表示は維持する
  - フルロード後はスクロールバーで「ファイル全体」を連続的に閲覧できること

## 9. メタデータ要件
- 作者・作成日はOfficeのプロパティを参照する

## 10. 性能 / 制限
- 1ファイルあたりの検出は最大50件で打ち切る（性能とUXのため）
- 大量ファイル時もUIが固まらない設計（非同期/進捗表示等）は後続で要件化

## 10.1 堅牢性（落ちない）
- 破損ファイル、読み取り不能、想定外の内容（制御文字混入等）があってもアプリはクラッシュしない
- エラー発生時は当該ファイルをスキップして処理を継続できる（検索全体は継続）

## 10.2 進捗表示
- 検索実行中はプログレスバーを表示し、進捗を100%（百分率）で表示する
- 進捗の定義は「調査対象ファイルの総ファイルサイズ（bytes）」を母数にした割合とする
  - 例: `処理済みbytes / 総bytes` を 0–100% に換算
- 併せて `処理済み/総数`（ファイル本数）も表示できること

### 10.2.1 進捗の加算ルール（仕様の明確化）
- `処理済みbytes` は、原則として「**ファイル単位の完了**」で加算する
  - 50件打ち切り（1ファイル最大50件）
  - スキップ（エラー/読み取り不能/除外条件）
  - 中断要求（ESC）を検知して当該ファイルの処理を終了
  などでも、当該ファイルの処理は完了扱いとして **ファイルサイズ分を加算**する
- 目的: 50件打ち切り等があっても進捗が100%に到達し、ユーザーの不安を減らす

## 10.4 検索の中断
- 検索中はESCキーで中断できる
- 中断してもアプリは落ちず、UIは操作可能な状態に戻る

## 10.5 文字コード（文字化け対策）
- `.txt` / `.md` / `.log` は文字化けしうるため、可能な限り自動判別・変換して表示する
- 日本語利用を前提に、判別/変換は **CP932（Windows-932）** を優先する
  - 優先順（整理）: **CP932（Windows-932）** → UTF系（UTF-8/UTF-16等） → それでも不可なら文字化けを許容して表示継続
- 文字コードが判別できない/不正な場合でも表示は継続する（文字化けは許容）
- プレビュー表示中のテキストについて、採用した文字コードを画面右下（画面の淵）に表示する

## 10.6 大容量ファイルの取り扱い（警告→OKで読み込み）
- 大容量ファイル（例: テキスト/ログ、Office、PDF）の読み込みは、閾値を超えた場合に警告を出し、ユーザーがOKした場合のみ読み込む
- ここでの「読み込み」は、主に **プレビュー側（フルロード/全体再構成）** を指す
  - 検索処理は原則としてユーザーに逐次確認を求めない（UX劣化のため）
  - 検索時の対象外制御は「詳細設定（Advanced） > ファイルサイズ上限」で行う
- 初期の警告閾値（提案）
  - 一般的なOfficeファイルは内容/画像量により大きく変動するが、数MB〜数十MBに収まることが多い
  - 本ツールの初期閾値は暫定で **20MB** とし、設定で変更可能とする

※以前の「1000KBで読み止め」は撤回し、警告フローに統一する。

## 10.7 コピー容易性
- 画面に表示される情報は、基本的にコピーできること（例: テーブルセル、プレビューのテキスト等）
- 画面上の文言・値は右クリックでコンテキストメニューを出し、「コピー」を実行できること

## 16. 配布/起動
- 最終的にexe化して配布する
- ただし初期フェーズでは、`uv` を用いて仮想環境（venv）を起動しアプリを実行できるバッチファイルを用意する

## 10.3 UI品質
- UIは常にモダンで、情報が過密にならず視認性が高いこと

## 12. 設計方針（DRY / 機能分割）
- DRY原則に従い、共通処理（I/O、文字正規化、例外処理、ログ、進捗通知等）は共通モジュールに集約する
- 実装は「機能ごと」にフォルダ/ファイルを分割する（例：検索、列挙、プレビュー、メタデータ、UI）
- UI（表示/操作）とドメイン処理（検索/抽出/変換）を分離し、テスト容易性と保守性を確保する

## 12.1 設定（Config）
- マジックナンバーを避けるため、閾値や挙動は設定ファイルで管理する
- 設定はXMLを採用し、Configフォルダ配下に配置する（例: `Config/config.xml`）
- 例: 大容量警告の閾値（MB）、ログレベル、対象拡張子、既定の検索条件など

### 12.1.1 `Config/config.xml` 必須キー（案）
実装ブレとマジックナンバーを避けるため、少なくとも以下を設定ファイルで定義する。

- `large_file_warning_threshold_mb`（int）: 20
- `search_max_matches_per_file`（int）: 50
- `logs_max_lines_per_file`（int）: 1000
- `logging_level`（string）: Information（Debug/Information/Warning/Critical）
- `target_extensions`（list）: [pptx, xlsx, docx, pdf, md, txt, log]

## 13. ロギング要件
- 機能ごとにログを仕込み、原因追跡に必要な情報を残す（検索、列挙、プレビュー、変換、メタデータ等）
- ログはレベル（Debug/Information/Warning/Critical）を持ち、例外時はスタックトレース相当を記録する
- ログはユーザーの作業を阻害しない（I/OでUIを固めない）

### 13.1 出力先/ファイル分割
- ログ用フォルダを作成し、ログはそこへ出力する（ポータブル運用を優先）
- 機能フォルダ単位でログファイルを分割する
  - 例: 検索機能フォルダ配下にPowerPoint/Excel/Word/PDF/Text等の実装があっても、検索機能としては単一のI/O（ログファイル1本）に集約する
  - 例: `search.log`, `enumeration.log`, `preview.log`, `metadata.log`, `ui.log`

### 13.1.1 ポータブル運用時の保存先
- ポータブル運用を基本とし、設定/ログは原則として実行ファイルと同じフォルダ配下に保存する
  - 設定: `Config/config.xml`
  - ログ: `logs/*.log`
- 実行ファイルの配置先に書き込み権限がない場合（例: Program Files）は、ユーザー領域へフォールバックする
  - 例: `%LOCALAPPDATA%\Unified-File-Search-Tool\Config\config.xml`
  - 例: `%LOCALAPPDATA%\Unified-File-Search-Tool\logs\*.log`

### 13.2 保持方針（上限1000行 + FIFO）
- 各ログファイルは最大1000行まで保持する
- 1000行を超える場合は、古い行から捨てるFIFO方式で更新する（最新1000行を保持）

### 13.3 ログレベル
- 少なくとも以下のレベルを持つ
  - Information
  - Warning
  - Critical
- 可能なら Debug も用意し、通常は抑制できること

### 13.4 ログ形式（機能横断で統一）
- 機能ごとのログであっても、1行の書式（フィールド構成）は共通化し、機能間で一体感のあるログにする
- 1行=1イベントとし、**JSON Lines（JSONL）** 形式で出力する（形式はこれに固定する）
- 最低限の共通フィールド（例）
  - timestamp（ISO 8601）
  - level（Information/Warning/Critical/Debug 等）
  - feature（search / enumeration / preview / metadata / ui 等）
  - event（開始/終了/スキップ/例外 等）
  - message
  - correlation_id（例: 検索1回を識別するID）
  - file_path（関係する場合のみ）
  - elapsed_ms（計測できる場合）

## 8.1 プレビュー（ページ相当の定義）
- PDF / Word / PowerPoint は、プレビュー上で「1ページ相当」の単位を持つ
  - PDF: ページ
  - Word: 1ページ相当
  - PowerPoint: スライド（= 1ページ相当）

※ページ相当の表示は「検索でのマッチ箇所」および「ページ/シート切替」の単位にも用いる。

## 6.3 正規表現（リッチ入力支援）
- 正規表現ON時は、ユーザーが入力欄に直接入力しても、支援UI（ボタン等）で挿入しても、同じ入力欄に反映される（双方向に同期）
- 正規表現入力支援として、以下のパターンをワンクリックで挿入できるボタンを提供する（少数精鋭）
  - `.*`
  - `\\s*`
  - `\\d+`
  - `^`
  - `$`
  - `|`
  - `(...)`
  - `(?:...)`
- 正規表現のオプションは以下の3つに絞る
  - Ignore case（大小無視）
  - Multiline（`^`/`$` を行単位にする）
  - Dot matches newline（`.` が改行も含む）

## 14. 性能・メモリ要件（設計上の優先事項）
- 大量ファイルでもUIが固まらない（バックグラウンド処理 + 進捗表示）
- 原則としてストリーミング/遅延処理を優先し、不要な全読み込みを避ける
  - ただし、ユーザーが明示的にフルロードを押した場合は当該ファイルのみ全体表示を許容する
- メモリ使用量が際限なく増えない設計（キャッシュの上限、使い終わったデータの解放方針）

## 15. リスク/検討事項（ディレクション観点）
- 「Office/PDFを現物に近くHTML再構成＋強調表示」は実装難度と計算量が高い
  - 仕様は維持しつつ、内部実装（レンダリング方式、位置合わせ、抽出精度）は段階的に検討する

## 11. 用語
- 「マッチ箇所」: 検索語が一致した位置（PDFならページ、Excelならシート等の単位情報を含む）
